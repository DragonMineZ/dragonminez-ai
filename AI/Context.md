# dragonminez-ai Context

Architecture facts. Keep them true: update this file when a structure below changes. Last checked 2026-10-17.

## What it is

BulmaAI is the Discord bot for the DragonMineZ Minecraft mod community (main server ~100k members). It covers:
- AI support tickets
- bug reports
- crash-log parsing
- Patreon beta whitelist
- release/dev-jar announcements and the build gate
- moderation (it replaced Dyno)
- a staff web panel

The mod repo is a sibling checkout at `../../dragonminez` (GitHub `DragonMineZ/dragonminez`).

## Layout (`src/bulmaai/`)

- `bot.py`: the client. Sets `SAFE_MENTIONS`, runs schema setup on startup, and loads `config.DEFAULT_INITIAL_EXTENSIONS`.
- `config.py`: the `Settings` dataclass. Settings come from env vars, then panel overrides in `data/settings_overrides.json`. `web/settings_meta.py` describes which settings the panel can edit.
- `cogs/`: Discord commands, listeners and `tasks.loop` jobs. Keep them thin.
- `services/`: logic and DB access (asyncpg). Highlights:
  - `mod_actions` (all moderation actions)
  - Ban appeals (`services/ban_appeals`, `web/routes_appeals.py` + `web/appeal_pages.py`, `cogs/ban_appeals.py`, `ui/appeal_cards.py`, table `ban_appeals`): on with `appeals_channel_id` set. Discord OAuth (identify only, the panel's client id/secret, state in an HttpOnly cookie; the session cookie is signed with `panel_session_secret` + ":appeals", path `/appeal/`, 2h; the token is never stored). The page checks the main guild (`fetch_ban`, else a running member timeout) and shows the reason/date and a form (why 20-1500, extra up to 500; CSRF field, per-IP in-memory rate limit); en/es/pt by Accept-Language; pages send `Referrer-Policy: same-origin` so form POSTs carry the Origin the middleware checks. One open appeal per user (partial unique index), a denied one blocks new appeals for `appeals_cooldown_days`. A submit records an `appeal` case and posts a card (rebuilt from the row on every change) with Accept / Deny / Ask a question (`banappeal:{accept|deny|ask}:{id}`, forms `banappeal_form:{deny|ask}:{id}`, Moderator+ in the main guild). Accept/Deny claim `WHERE outcome IS NULL`; Accept runs `perform(unban|untimeout, source="appeal")` and gives the claim back on failure (a 404 still counts); Deny records an "Appeal denied" note. A question shows on the status page; the member's answer updates the card and is posted under it. The status page is how they hear back (pending, question, accepted + `appeals_invite_url`, denied + staff reason + next date). Ban and timeout DMs in the main guild link to the site while it's on; otherwise they carry no appeal button (the old in-Discord appeal flow is gone)
  - `ai_client` (shared `AsyncAnthropic` client; the `anthropic` SDK is the only AI provider) + `ai_tools` + `ai_guard` (AI calls, tools, output screening). The support AI's fast pass is `claude-haiku-5-5` at low effort; an unsure (answer below `ai_support_escalation_confidence`, default 0.6), repeated or handed-off reply escalates to `claude-haiku-5-5` at high effort, and only what that still can't settle goes to `claude-sonnet-5-5` at `ai_support_effort` (default low) (`ai_budget.escalation_routes`, budget permitting); a handoff never goes to Sonnet (it needs staff, not a bigger model). `_escalation_reason` (repeat, clarify_loop, no_reply, no_markers, handoff, low_confidence) is stored as `escalation_reason` in the escalation trace's `request_metadata`, next to the `confidence` column; every pass can use tools, including `search_knowledge`. `ai_oneshot` holds the single-shot helpers (summaries, translations, titles)
  - Answer controls: the support model's `ask_requester` tool (`ai_tools`, not strict; local, validated by `ui/ai_asks.validate_ask`: limits, every model-written label screened like the reply, invalid parts dropped, errors returned to the model) attaches `choices` (buttons), `select` (one dropdown) or `form` ("📝 Fill in" opening a `DesignerModal` of up to 5 Label-wrapped short/long text, select or radio fields). `ai_client._last_ask` hands the last valid spec to the result (`AgentResult.ask`) unless the reply is a handoff or isn't sent; the cog puts the controls on the answer's last card (`ai_ask:{kind}:{requester_id}:{index}`) and saves the spec in the `ai_asks` table (`services/ai_asks`: message_id, spec, language, answered_at). Clicks and modal submits (`ai_ask_form:{message_id}`) are routed in `ai_tickets.on_interaction`, read the row, pass the typed path's gates, and claim it (`answered_at IS NULL`, first wins). The answer edits the card (controls gone, `-# ↳ <@user>: **label**`, or one `-# ↳ <@user> · Field: **value**` line per form field) and is answered like a typed reply; that card text is the record, read back as the requester's turn in history and transcripts (`ai_tickets._choice_turn`). Static texts are en/es/pt by the row's language. Kind `file` (`what` log/screenshot/any, 1-3 files) is a "📎 Upload" button opening a `FileUpload` modal (`ai_ask_file:{message_id}`; attachment ids resolved from `resolved.attachments`), plus for logs an anyone-may-use "Where is it?" select answering ephemerally from `ui/log_help_views` plus launchers; the submit (same gates and claim, total size under the guild's upload limit) reposts the files on a card of `-# ↳ <@user> uploaded **name**` lines read back as the uploader's turn with the files' analyses, records the same lines on the question card, has `LogParserCog.parse_upload` / `DmzDebugCog.post_cards` post their cards (no 🔍 approval, no AI diagnosis, corpus credits the uploader), then answers with the repost's attachments on the stand-in so screenshots get analyzed. Kind `steps` (2-8 steps) shows the list in a TextDisplay of its own (`ai_asks.CONTROLS_TEXT_ID`) plus "✅ Done" / "❌ Still broken" for the current step (index = step * 2 + button); Done moves `ai_asks.progress` on (`services/ai_asks.move`, compare-and-set, no AI, a click on an outdated card just refreshes it), Still broken or the last Done claims the row, records `**Step N didn't work:** step` / `**Did all the steps (1-N)**` and hands back to the AI (read back in English; a card in progress reads back "I did steps 1-k." from its buttons' custom ids). The separate `offer_action` tool (`ai_asks.validate_action`; `channel_kind` is set by `ai_client._hydrate_tool_args`, and the cog drops what `ai_asks.allowed_in` refuses) puts one button (kind `action`, optional "No thanks") that claims the row and runs an existing flow: `get_staff` (tickets: `_mark_ticket_escalated` + `_ping_escalation_roles`, like "No, I still need help"), `open_ticket` (public channels: the panel's `TicketModal`, or its category select; members with an open ticket get its link), `link_patreon` (`PatreonWhitelistFlowCog.send_link_prompt`, /patreon link's answer), `report_bug` (public channels and DMs: the click claims nothing and opens a modal, `ai_ask_bug:{message_id}`, of title / what happened / steps / version pre-filled from the model's prefill fields, which `validate_action` screens like labels; refused ephemerally when bug reports are off (`bug_reports_enabled`), the forum `bug_report_forum_channel_id` or `BugReportsCog` is missing or the requester isn't in the forum's server. The submit claims the row and posts in the forum (`ForumChannel.create_thread`, plain text: "Reported by <@id> with Bulma" plus the defanged fields, at most 2000 characters, no pings) with up to 3 of the requester's logs and screenshots from the conversation the card belongs to (thread context or the public window before the card; their own messages' files and Bulma's reposts of their uploads, newest first, within the forum server's upload limit), records `-# ↳ <@id>: **Reported the bug** → <post link>` on the card (read back without the link), then `BugReportsCog.triage_thread` triages it with the requester as reporter, so the triage card's "Open a ticket" is theirs; the forum listener skips posts whose starter is a bot's. A failed post releases the row). `/ask` runs without either tool (`LOOKUP_TOOL_NAMES`)
  - "Ask Bulma" message command (`AITicketsCog.ask_bulma`, guild + bot DM contexts): `_ask_bulma_gate` applies a typed request's gates (public: our servers' text channels and support threads, `can_use_ai_support`, not a closed ticket; tickets: AI on for the ticket; DMs: a member with support access; plus `ai_support_enabled`, `ai_budget.is_paused`, the per-user rate limit), refuses other bots' and webhooks' messages (our own cards are fine) and empty ones, ephemerally (ticket language in tickets, else the reader's language). Past them the click gets an ephemeral "On it…" and `_answer_pick` runs `_answer_support` in the background on an `_AskedMessage`: the invoker as author, `Help me with this message from {name}:` plus the target's text (`_message_text`: own, card, forwarded) as content, the target's files (forwarded too) as attachments, the target's id. `_build_history` skips the target's own place in the channel (`skip_id`) and appends that stand-in as the last requester turn, with the screenshot/log analyses; a context line says whose message it was. The answer is a normal public card (public guard, fallback text, no pings)
  - Answer feedback (`ui/ai_feedback`, `services/ai_feedback`, setting `ai_answer_feedback_enabled`): the last card of a plain answer (kind answer or unmarked, no controls, not a fallback text, never in tickets) outside tickets, and of a public `/ask` answer, gets 👍/👎 (`ai_fb:{requester_id}:{up|down}`). Sending saves an `ai_feedback` row (message_id, channel_id, requester_id, response_id, helpful NULL, language, created_at); the requester's click (`_handle_feedback`, `while_busy`) sets helpful through an upsert `WHERE helpful IS NULL` (first wins; a missing row still records) and swaps the row for `-# Thanks for the feedback!` (en/es/pt), which `_card_text` skips so it never reaches history or transcripts. The weekly report counts the week's rated answers
  - "Answers to fix" (`ui/feedback_fix`, handled in `cogs/support_info.py`): right after the weekly report post (inside its claim, never with `/support-report`), `cogs/support_report._post_answers_to_fix` posts a header card plus one card per answer for up to 10 of the week's unreviewed 👎 answers (`ai_feedback.answers_to_fix`: rows with a response id, newest first, paired with their reply's trace from `support_traces.get_reply_traces`, which skips drafts and decodes `input_json`; the question comes from `support_faq.support_trace_to_faq_source`). One card per answer, so each collapses on its own and no message nears the component or text limits. A card shows where (`<#channel>` or DM), language, day, the question (~300) and Bulma's reply (~500) as one-line excerpts (defanged: no pings, no clickable links or previews, markdown escaped), plus "✏️ Write the right answer" / "Skip" (`fbfix:{write|skip}:{answer message id}`, routed in `SupportInfoCog.on_interaction`, `in_main_guild` + `is_staff`). Write opens a form (`fbfix_modal:{id}`, routed by custom id: title pre-filled from the question, answer, kind select default permanent, optional days for temporary); the submit claims the row (`ai_feedback.claim_review`: `reviewed_at`/`reviewed_by` `WHERE reviewed_at IS NULL`, first wins), calls `support_info.add_info(status="active", source="feedback", created_by=staff)`, stores `info_id` and collapses the card to "✅ <@staff> → support info #id: title". A validation error releases the claim (`release_review`, only your own claim without an `info_id`). Skip claims and collapses to "⏭️ Skipped by <@staff>". A click on an answer someone else handled shows their outcome plus "Someone already handled this one."
  - Threads (`ai_tickets`): `_channel_kind` (ticket / dm / public; threads are never tickets) is the one place the kind comes from. `_is_support_thread` accepts public threads (forum posts count) of our servers except the bug-report forum's posts (`bug_report_forum_channel_id`, `cogs/bug_reports` owns those); private and news threads are ignored. They are public everywhere: pings, Ask Bulma, controls, feedback, the public guard; uploads stay refused. Thread history (`_thread_context`) has no age cutoff: the thread's newest 30 messages after what led into it (`_thread_lead`: a forum post's first message, fetched only when outside the window; the text-channel message a thread was made off, id == thread id). Moving: a real answer (not the fallback text) to a follow-up in a public text channel, i.e. a typed reply to one of Bulma's answer cards (her card with `AI_FOOTER`) or an answer on its controls (pick, form, steps outcome; `_ChoiceMessage.card`), goes into a new thread (`_open_help_thread`, 1-day auto-archive) made off the reply, or off the card for a control answer, so the starter ends the channel's conversation. Name: the question the card answered (`_ASK_QUESTIONS`, an Ask Bulma reply target, else the requester's latest message before the card), else the reply's text, else the requester's name, cleaned by `_thread_name` (no mentions/links/markdown, 90 chars, banned words fall back). Creation or send failures answer in the channel. Help threads (`_is_help_thread`: Bulma owns it, parent is a text channel): `_thread_lead` adds the channel's context window counted back from the starter, so the question and her earlier answer stay in view; `_help_thread_requester` reads who it is for off the starter (the reply's author, or the user on the card's answer line; anything else, like a dev jar feedback thread, has none), cached per thread and re-read after a restart. That member is answered there without a ping (ticket-like: acks skipped, no intent check, still public guards and AI access); others still ping. Pending keys stay on the trigger's channel; the move sends under the new thread's lock
  - Staff copilot in tickets (`ui/staff_copilot`, `services/staff_copilot`): the welcome card's row (`ticket_views.control_row`, swapped whole on every state change) ends with "📋 Summary" and "✍️ Draft reply". Both: HELPER gate on an open ticket, refused at once ("AI is paused for today.") when `ai_budget.is_paused`, no `while_busy` (it would lock the owner's Close/Solved while the AI works): the click defers ephemerally with "thinking", a second click by the same staff member on that ticket meanwhile gets "Already working on it." (`TicketsCog._copilot_working`), and the answer is an ephemeral card. Summary: `AITicketsCog.ticket_summary` → `_collect_transcript` lines → `staff_copilot.summarize_so_far` (one-shot JSON on `ai_ticket_summary_model`, anonymized like `summarize_ticket`, fields defused and link-stripped): problem, tried, current state, next step, in English. Draft: `AITicketsCog.draft_reply` runs `run_support_agent` on the ticket history (`_ticket_history` with the owner as requester and `user_id`, `LOOKUP_TOOL_NAMES`, `workflow_prefix="staff_draft"`, the ticket language, a context line saying a staff member wants their next reply); the ephemeral card holds the draft (TextDisplay id 820) with Post / Edit & post / Discard (`staff_draft:{post|edit|discard}`, routed in `TicketsCog.on_interaction`, the draft read back from the card, no DB). Edit & post opens a modal pre-filled with it (`staff_draft_edit:{channel_id}`). Post and the submit re-check the gate, then `TicketsCog._post_staff_reply` sends a public card of the text (mentions defused) plus `-# ✍️ <@staff>` (TextDisplay id 821, no pings), calls `AITicketsCog.staff_replied` (drops the pending AI answer) and `note_ticket_message(channel, staff)`. `AITicketsCog._signed_turn` reads such a card as that staff member's turn (speaker kind staff, their name) in history and in `_collect_transcript` (so summaries and knowledge too); `_card_text` leaves the signature out, and only the component id makes a card staff's. Translation: `AITicketsCog.on_message` hands every human (Member, not bot or webhook) message in an open ticket to `_translate_message` (background task; edits aren't translated; off with `ai_support_enabled` too; non-staff still get their usual handling): setting `ai_ticket_translate_staff`, not paused, a known owner (`_is_ticket_owner`; unknown owner = skip), `staff_copilot.worth_translating` (3+ prose words). The owner's messages go to the staff: targets are the languages (`i18n.user_language`, role or English) of everyone besides the owner who wrote in the ticket (`_ticket_participants`: the last 100 messages read once per channel, people only plus the staff on signed draft cards, then kept in memory by `_translate_message` and `staff_replied`; `_staff_languages`, English before anyone wrote), minus the message's own language (`staff_copilot.text_language`, else the ticket's); none left = no call; else `translate_owner_text` (one call, JSON `translations` keyed by language code, each dropped when empty or still another language), every text screened (one block drops the card), and `ui/staff_copilot.translations_card` (one language = the card below with its footer in that language; several = one TextDisplay id 822 of `-# 🇪🇸 Español` labelled blocks sharing the room evenly, English footer). Anyone else's message: `staff_copilot.translation_source` (the prose without code, links, mentions and emoji has at least 3 words, and one other language's marker words, plus letters only it writes, outscore the ticket language's and the third one's; that language is the source), then `translate_staff_text` (`ai_translation_model`, support-tone prompt naming both the source and the ticket language, JSON with only the translation; dropped when it still reads as another language than the ticket's), `screen_reply`, then `_post_translation`: through the channel's webhook (`_translation_webhook`: one the bot created there, else a new "Bulma Translate"; cached per channel in memory, dropped on failure; the bot needs Manage Webhooks in the ticket category) with the author's display name (plus a "Staff" tag when they are staff) and avatar, a card quoting the original (`clean_content`, ~1000 chars, TextDisplay id 823) above a separator, the translation (TextDisplay id 822) and `-# 🌐 Translated from {Language}` in the ticket language; no pings. When the card holds all of the message (text only: no files, stickers or poll, at most `ORIGINAL_LIMIT` characters) the footer ends ` · <@author>` and the original is deleted after the send. If the webhook can't be had or used, the same card without the quote goes out as Bulma's reply to the message (logged at INFO) and the original stays. `_is_translation` (Bulma's or a webhook's message with id 822) keeps them out of `_serialize_message` and `_collect_transcript`, except a card with the author in its footer: `_translated_turn` (`staff_copilot.translated_original`: id from the footer, the unquoted 823 text) reads it as the author's turn in their original words (staff kind when they are staff), and `_ticket_participants` counts its author; webhook posts are bots to every listener; the hosted HTML transcript keeps them
  - Mod source tools (`services/mod_source`, lookups in `ai_tools`, so also in `/ask` and staff drafts): `list_mod_files(area, folder)` and `read_mod_file(path, query, start_line)` read the mod repo (`GITHUB_DEFAULT_REPO`) on setting `mod_source_branch` (default `main`) through the GitHub App: one Git tree call (`GitHubService.list_tree`) for listings, the Contents API per file. Only the allowlist `mod_source.AREAS`: config = `common/config/*.java` (one level), defaults = `data/dragonminez/previousConfigs/**` (the shipped upgrade baseline; same layout as a game's `config/dragonminez/`, whose paths map onto it), commands = `server/commands/*` (DMZPermissions too) + `server/DMZServer.java`, lang = `assets/dragonminez/lang/en_us.json`, quests = `data/dragonminez/previousQuests/**`; `.java`/`.json` only, plain relative paths (no `..`, `.`, empty parts, absolute paths, `%` or other odd characters). Listings stop at 80 files and then show every folder with its count (pass one as `folder`). Reads return numbered lines: with `query` (case-insensitive, up to 100 characters) the matching lines with 3 lines of context, merged; else a window from `start_line`; at most ~6000 characters (`truncated`), lines cut at 300. Errors come back as `{"error"}` (not allowed, not found, GitHub failed). Tree and file texts are cached in memory for 10 minutes per (branch, path)
  - Code notes (`services/code_notes`, `code_notes` table, settings `code_notes_enabled` / `code_notes_model`, default Haiku): `BuildGateCog._queue_code_notes` runs for every verified push event to the mod repo (any branch, before the build-gate filter, off when disabled or `ai_budget.is_paused`) and hands the push's new commits (`push_commits`: this repo, branches only, each sha once, not `distinct: false`, no merge commits) to `process_commits` in the background: skip a sha already stored or in flight, `GitHubService.get_commit` for the diff, `build_diff` (source files only: .java/.json/.toml/.gradle/.kts/.properties/.lang/.mcmeta, no generated/build paths; 9k chars per file, 40k total, truncation noted), one Haiku call with JSON output (what / why / areas / config_keys) with the mod repo's `AI/Context.md` as cached background (read through the Contents API, cached 1h) and the commit text as untrusted data; `parse_note` stores the text with the files and a full-text index. Staff only: `/devlog [query]` (`cogs/devlog.py`, staff + main guild, ephemeral) and the `search_code_notes` tool, which is in `ai_tools.STAFF_DRAFT_TOOL_NAMES` only (not in `SUPPORT_TOOL_NAMES` / `LOOKUP_TOOL_NAMES`; `ai_client` refuses a staff tool that isn't enabled), used by `AITicketsCog.draft_reply` alone. Never posted to GitHub, never in `knowledge_docs`
  - `ai_budget` (two daily token pools: small = haiku, big = all other models; seeded at startup from today's `ai_usage` rows, or from `support_traces` while the ledger is empty). `record_response(response, feature)` also hands every call to `ai_usage`
  - `ai_usage` (per-call ledger, table `ai_usage`): every Claude call with its feature label (`FEATURE_LABELS`; support runs use their workflow name, so support answers, escalations, log diagnosis and staff drafts split apart), model, input/output/cache read/cache write tokens, web searches and a list-price `cost_usd` (`PRICES`: Haiku 5.5 $0.10/$0.50 per M, $0.50/$2.50 when the prompt incl. cache is over 100K; Sonnet 5.5 $2/$10; cache write 1.25x and read 0.1x the input price; $0.01 per web search; unknown models priced like the dearest known one). `record` is sync and never raises: rows queue in memory (cap 5000, oldest dropped) and a task the bot starts after DB setup flushes them every 5s with one executemany (failures dropped, logged at INFO; flushed again on close). Startup (`prepare`): deletes rows older than 400 days, and when the table is empty backfills 90 days of `support_ai_traces` (`backfilled = TRUE`, approximate: support calls only). Settings `ai_monthly_budget_usd` (100) and `ai_budget_cycle_day` (1-28, UTC day the credit renews)
  - `knowledge` (Postgres `knowledge_docs` table, full-text search; sources: mediawiki, ticket, faq, local `data/knowledge/*.md`)
  - Ticket panel (`ui/ticket_views`, `cogs/tickets`): `CATEGORIES` (order = panel order; `mod_only` drops Helpers from `build_overwrites` and switches `AITicketsCog._ping_escalation_roles` to `panel_moderator_role_ids`; `ai_reply` gates the first AI answer) with their words per language in `CATEGORY_TEXT[lang][key]` and member messages in `TEXT[lang]`. `on_panel_select`: one language role → `TicketModal(category, lang)`; else the ephemeral `form_language_card`, whose `ticket_form:{key}:{lang}` buttons (`on_form_language`) open the modal. The modal passes `language=` to `create_ticket`, which makes it `tickets.language`; answers are stored with English field labels. Each pick re-sends `panel_view()` on the public panel, so old panels pick up new categories
  - Ticket log: every successful archive (`AITicketsCog._close_ticket`, so each close and re-close) posts `ui/ticket_views.ticket_log_card` to `ticket_log_channel_id` (default the ticket-logs channel, None = off): number, category, owner, closer, language, opened, message count, solved, the AI summary (title/problem/resolution) and a Transcript link button; English, no pings, failures only logged
  - `tickets`, `ticket_transcripts` (`knowledge_filename` links a transcript to its `knowledge_docs` row). `tickets.language` is the ticket's support language (member-facing text via `ui/ticket_views.TEXT`, AI via `ai_tickets._ticket_language`); `note_ticket_message` tracks the owner-reply countdown with one conditional UPDATE per ticket message
  - `support_info`: staff-curated entries (`support_info` table). Temporary ones (current issues, optional expiry) and permanent ones (custom answers); every active entry goes into the support AI's developer message (`ai_client._build_data_input`, 60s cache). `cogs/support_info.py` posts active temporary entries to `support_info_channel_id` every 24h (replacing the previous post; `support_info_post` row), runs `/info`, and owns the staff review card for AI suggestions (`finish_suggestion`) and the "Answers to fix" buttons and form. `support_info.source` is `manual`, `ai` (a suggestion) or `feedback` (written from an Answers to fix card). The ticket summary may carry a `support_info` suggestion; it is stored as `suggested` only on a staff Solved close. Panel page: `web/routes_support_info.py`.
  - `support_report`: weekly staff report (`cogs/support_report.py`, hourly loop, posts Mondays from 09:00 UTC to `support_report_channel_id`, none = off; `/support-report` builds it on demand, ephemeral). Numbers from `ticket_transcripts`, `support_ai_traces` (spend is an estimate of support replies only) and `ai_feedback` (👍/👎 counts and % helpful, no line without ratings), plus one Sonnet call (`ai_support_escalation_model`) over the anonymized summaries and handed-off questions. The last post is the `support_report_posts` row, claimed atomically. The weekly post is followed by the "Answers to fix" cards (see Answer feedback); their failure is only logged and never re-posts the report.
  - `log_pages` (redact + render + 24h storage for uploaded logs). The `log_parser`/`dmzdebug` cogs post the cards; their `summary_for_ai` text is what the support AI sees for a log attachment (`ai_tickets._log_analyses`), never the raw file. `utils/log_parser.parse_log` also sets `LogReport.root_cause` (deepest `Caused by:`, the exception chain and, from a mixin config or the first mod stack frame, the culprit mod/jar), which leads `summary_for_ai` and the card's "Likely cause" block; the mod list also comes from latest.log's "Loading N mods" block, `LogReport.jars` from "Found mod file" lines, "Mod Loading has failed" reports take the cause from the first `-- MOD x --` section, a mixin config prefix is the culprit when its id isn't in the mod list, and `LogReport.hints` from `utils/crash_hints.RULES` (known fixes learned from the log corpus) show as the card's "💡 Known fix" block and lead `summary_for_ai`.
  - Crash-log AI diagnosis: after posting a log card with errors, `log_parser._add_diagnosis` runs `ai_client.run_support_agent` on `summary_for_ai` (no tools but `search_knowledge`, `workflow_prefix="log_diagnosis"` so traces are `log_diagnosis`/`log_diagnosis_escalation`/`log_diagnosis_draft`, outside the support_* exports) and edits the card to add the "AI diagnosis" block. No placeholder; any skip or failure leaves the card as posted. Per-uploader rolling 24h limit in `log_ai_uses` (`services/log_ai_quota`, purged by the hourly `purge_log_pages` loop); settings `log_ai_*`.
  - `log_corpus` (+ `cogs/log_corpus.py`, `ui/log_corpus_views.py`): `log_parser._collect` hands each analyzed main-guild log to `LogCorpusCog.collect_later` (background task). It saves the redacted log and a `.json` (versions, root cause, uploader text, up to 10 messages from the 30 min before) to `data/log_corpus/`, a `log_corpus_entries` row, and a notice card with an admin Exclude/Include toggle in `log_corpus_channel_id` (None = off). At `log_corpus_ping_threshold` waiting logs for one DMZ version Bruno is pinged once (`log_corpus_pings`); Download .zip or `/log-corpus` adds the chat from the 48h after each log, posts the .zip(s) (split by the guild upload limit) and then marks rows `bundled_at` and deletes the files. The hourly `purge_log_pages` loop drops rows and files older than 60 days. `scripts/log_corpus_eval.py` re-scores an extracted corpus zip against the parser (posted vs. now, hints, unexplained cases).

Names autocomplete per category
  - `build_gate`, `patreon_*`
  - Mail inbox (`services/mail_inbox`, `ui/mail_cards`, `cogs/mail_inbox.py`, table `mail_messages`): one mailbox (env `MAIL_USER` / `MAIL_PASSWORD`, Hostinger by default: `mail_imap_host` 993, `mail_smtp_host` 465) mirrored into `mail_channel_id`; on only when all three are set. A 2-minute loop reads INBOX read-only (`SINCE` yesterday, newest 25, `BODY.PEEK`: never marks read, moves or deletes), skips Message-IDs already stored and mail from `MAIL_USER`, inserts `ON CONFLICT (message_id) DO NOTHING` and posts a defanged card with "↩️ Reply" (`mail:reply:{id}`); a failed post deletes the row so the next poll retries. Reply opens a form (`mail_form:reply:{id}`); main-guild admins only (`is_admin`). The submit claims the row (`WHERE replied_at IS NULL`, first wins), sends over SMTP (Re: subject, In-Reply-To/References), releases the claim on failure, and turns the card green with the reply quoted. ## Data

- `scripts/schema.sql` runs on every startup (`services/db_schema.ensure_schema`). Schema changes are idempotent `CREATE ... IF NOT EXISTS` / `ALTER ... ADD COLUMN IF NOT EXISTS`. There are no migrations.
- `data/`:
  - `knowledge/`: local knowledge `.md` files, loaded into `knowledge_docs` (source `local`)

  - `settings_overrides.json`
  - ticket transcripts (gitignored)
  - `log_pages/`: redacted log/dmzdebug viewer pages, expired by file mtime after 24h (`services/log_pages`, swept hourly by the `log_parser` cog; gitignored)

## Deploy

- DigitalOcean VPS, systemd unit `dragonminez-ai-discord.service`, run from a venv. Logs: `journalctl -u dragonminez-ai-discord.service`.
- Agents have no SSH access. Give the user commands to run.
- `self_update` cog: a push webhook on this repo (`/dmz-bot-update`, signed with `GITHUB_PUSH_WEBHOOK_SECRET`, served by the release webhook server) triggers an immediate check of origin; a 10-minute poll is the fallback. Hot-reloadable commits apply on their own; the rest wait for "Pull & restart" from Discord.
- `scripts/dmz-bot`: console CLI over a chmod-600 Unix socket (see Memory: VPS console).

## Build gate

Pushes to the mod repo that change `.java` files hit `/dmz-github-push` (needs `GITHUB_PUSH_WEBHOOK_SECRET`). Staff-devs approve in Discord, and then the bot dispatches the mod's `dev-jar-upload.yml` (workflow_dispatch only).
- Pushes to the same branch within 30 min fold into one prompt.
- The prompt auto-closes after 1h.
- `/buildjar` offers the last 3 pushes.
- `compile-check.yml` in the mod repo is the safety net.
